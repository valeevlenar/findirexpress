# Маркировка в FindirExpress

ИП получает собственный `marking_participants.id` без `seller_id`. Профили двух ООО связаны с их существующими `sellers.id`. Профиль ИП привязывается к существующему Telegram-пользователю через `marking_access`. Разрешённые пары отправителя и получателя хранятся в `marking_routes`.

## Подготовка тестовой базы

Применить `migrations/20261123_marking.sql` к тестовой PostgreSQL, в которой уже есть таблицы `users` и `sellers`. Затем задать `FINDIREXPRESS_MARKING_TEST_DSN` в формате `postgresql://...` и выполнить из корня проекта следующую команду с тестовыми данными.

```text
python -m app.marking.provision --issuer-inn 100000000012 --issuer-name "Тестовый ИП" --owner-tg-id 900001 --recipient-seller-ids 101 102
```

Оба `seller_id` и Telegram ID должны существовать в целевой базе. ИНН и названия получателей берутся из выбранных кабинетов. Повторный запуск с теми же параметрами сохраняет идентификаторы и связи. Профиль и обе связи создаются атомарно.

## Проверка в Codex

> Переключись на `origin/codex/chestny-znak-schema`. Подними отдельную локальную PostgreSQL и установи зависимости из `requirements.txt`. Направь `DBURL` и `FINDIREXPRESS_MARKING_TEST_DSN` только на неё. Создай базовые таблицы через `app.database.models.async_main()` и добавь вымышленные записи в `users` и `sellers` для ИП и двух ООО. Примени миграцию и дважды выполни команду создания профиля. Проверь, что у ИП нет `seller_id`, обе связи с ООО существуют, а повтор сохраняет идентификаторы. Создай фиктивный заказ и шифротекст кода в контуре `test`. Проверь запрет резерва кода для двух передач и для другого контура. После имитации принятия УПД проверь владельца, закрытие резерва и запись в журнале. Не запускай `main.py`, не вызывай Честный знак и не подключайся к продакшену.

Перед запуском ботов в `.env` нужно задать `ALLOWED_TELEGRAM_USER_IDS` двумя разными числовыми ID из `users.tg_id`. При пустом или некорректном списке боты не запускаются. Список применяется до обработчиков команд, регистрации, ссылок-приглашений и кнопок во всех трёх ботах. Приложение обрабатывает входящие сообщения только в личных чатах.

## Заказы, коды и передачи

- Перед созданием заказов понадобится запись в `marking_connections` для ИП и соответствующего контура. Настройка профиля сама по себе к СУЗ не обращается.
- В заявке сохраняются локальный UUID и внешний ID заказа СУЗ. При неопределённом результате отправки используется статус `submission_unknown` до сверки с СУЗ. Код идентифицируется парой GTIN и серийного номера внутри контура.
- В `encrypted_code` передаётся уже зашифрованный полный код, включая разделители в исходном представлении. Ключи шифрования, токены СУЗ и УКЭП хранятся вне этих таблиц. Получение и расшифровка кодов относятся к будущей интеграции.
- `reserve_code` привязывает код отправителя к черновику и записывает событие. Один код может иметь только один активный резерв. `confirm_transfer` вызывается после сверки принятого документа ГИС МТ и всех его кодов. Она атомарно меняет владельцев, закрывает резервы и добавляет события. Отправка, подписание, отклонение и отмена будут записываться отдельными операциями при подключении ЭДО.
- История ведётся только добавлением. В ней отдельно хранится время источника и время записи. Исправление представляется новым событием; исходные записи сохраняются. Время подтверждения требуется с часовым поясом.
